00 / THE OBJECTIVE

Growing conditions are connected.
Monitoring should be, too.

A useful field picture needs more than one number. GreenGuardian brings local signals and regional context into the same view.

⌕

The challenge

Temperature, moisture, light, rain, and weather each describe a different part of the environment. Looking at them separately can make it difficult to form a quick overall picture.

✳

The project objective

Develop a mobile monitoring platform that can sample changing locations across a field, combine environmental data with regional weather, and present crop suggestions as decision support. The long-term vision is to reduce routine field visits—not to replace agronomic judgment or claim fully autonomous farming.

01 / TWO-CONTROLLER ROBOT ARCHITECTURE

Two controllers.
Two different jobs.

The system concept separates mobility and actuation from environmental sensing and network telemetry, so each controller can focus on its own timing-critical work.

MOBILITY + ACTUATION / ARDUINO NANO

Move, stop, probe, retract

The Arduino Nano sketch drives the robot through timed motor sequences and moves a servo between 0° and 120° to deploy and retract the soil probe. The intended sampling cycle is to stop at a location, lower the probe, take a reading, retract it, and then move to another point.

  • Mobility base field traversal
  • Servo control probe deployment
  • Repeated sampling multiple locations

SENSING + TELEMETRY / ESP32

Measure, package, transmit

The ESP32 reads the environmental sensor payload and uses built-in Wi-Fi to send readings to the web application. Keeping it focused on acquisition and communication separates telemetry from motor control.

  • DHT11 air temperature + RH
  • Rain module + LDR rain + light signal
  • Soil probe moisture at sample point

THE AUTONOMY LOOP

Cover more ground, one sample at a time.

The mobility base turns a fixed sensor station into a roaming field observer. At each planned stop, the probe can collect a new soil reading before the robot continues its route.

IMPLEMENTATION STATUS

The repository now includes separate Nano and ESP32 sketches. The Nano sketch runs timed motor and servo actions; the ESP32 sketch independently reads sensors and posts JSON to Flask. The sketches do not yet define a Nano-to-ESP32 communications protocol or synchronize probe movement with a confirmed soil reading. The Nano's timed movement also has no encoder or position feedback for closed-loop navigation.

02 / SOFTWARE DATA PIPELINE

From a field reading
to a broader picture.

The current software path carries ESP32 measurements into a Flask service, enriches them with weather, and returns structured results to the dashboard.

01⌁

Sense the environment

An ESP32 reads temperature, humidity, rain, ambient light, soil moisture, and ultrasonic distance from connected sensors.

02↗

Bring in context

A Flask server receives the readings over Wi-Fi and combines them with weather and air-quality information from OpenWeather.

03✳

Explore crop options

A scikit-learn model predicts a crop from climate features. Gemini can offer three additional suggestions using the wider context.

DATA FLOW

The current ESP32 sketch sends JSON to Flask about every five seconds when Wi-Fi and the DHT reading are available. Flask validates the payload, updates the latest in-memory readings, applies simple sensor labels, and runs the crop classifier. OpenWeather refreshes about every ten minutes; Gemini requests are limited to at most once per minute. The checked-in app is configured as a local-network Flask server, not a deployed cloud service.

DATA NOTE

The model training data is based on Atharva Ingle's Crop Recommendation Dataset (Kaggle), licensed under Apache 2.0; the N, P, K, and pH columns were removed. Rainfall is estimated from the current OpenWeather one-hour precipitation value multiplied by 24, not measured daily rainfall. Sensor thresholds are configurable starting estimates. The current dashboard shows the latest values held in server memory; persistent farm-wide history is part of the broader product vision, not current storage behavior.

04 / THE INTELLIGENCE LAYER

One prediction.
Three more perspectives.

The model and the language model serve different roles. Keeping those roles distinct makes the output easier to interpret.

MACHINE LEARNING / CLASSIFICATION

Random Forest crop prediction

The included scikit-learn model is a Random Forest classifier trained from the prepared crop-recommendation dataset. The training script uses an 80/20 train/test split and fits 100 trees; its prediction is restricted to the crop labels in the dataset. The script currently does not calculate or report test-set performance metrics.

  • Temperature model input
  • Humidity model input
  • Rainfall model input

GENERATIVE AI / ADDITIONAL OPTIONS

Gemini adds a separate view

In the current implementation, Gemini receives the latest sensor summary, local weather, air-quality category, and model prediction. It is prompted to return exactly three ranked crop options, which may include crops outside the classifier's labels.

This is crop-option generation, not a validated diagnosis or a treatment engine. The broader AI agronomist concept would require additional domain logic, evaluation, and safeguards before offering actionable crop-care instructions.

Ranked suggestionsSeparate from model outputInformational only
INTERPRETATION

Only temperature, humidity, and estimated rainfall are passed to the scikit-learn classifier. Rain, light, soil moisture, and distance are displayed as field context; they are not classifier features in the current implementation. The training script creates a train/test split but does not report evaluation metrics.

05 / ASSUMPTIONS & NEXT STEPS

Useful starting points.
Honest about uncertainty.

The project is a monitoring and decision-support prototype. Sensor cutoffs and derived values should be checked against the real installation.

Rain sensor

ADC below 2000 → wet

ADC 2000 or above → dry

Light sensor

ADC below 1500 → bright

1500–2999 → moderate / dim

ADC 3000 or above → dark / shaded

Soil sensor

ADC 0 → no sensor detected

1–1499 → very wet / saturated

1500–2799 → moist / optimal; 2800+ → dry

CURRENT LIMITATIONS

What the results do not claim

  • Rainfall is estimated not directly measured
  • ADC labels are starter cutoffs not calibrated
  • Predictions are not field trials no yield guarantee
  • Latest readings are in memory no history storage
